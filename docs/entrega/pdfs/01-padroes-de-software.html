1. Introdução e Contextualização do Sistema

O ArenaHub é uma plataforma moderna e resiliente de gestão de eventos e comercialização de ingressos focada no cenário de esportes eletrônicos (e-sports), convenções gamers e meetups tecnológicos. O sistema foi concebido para suportar cargas massivas e picos intensos de requisições concorrentes (cenário típico de abertura de lotes de grande porte), garantindo integridade financeira estrita, ausência total de overbooking e alta disponibilidade dos serviços essenciais.

Em estrito alinhamento com as diretrizes pedagógicas e técnicas ministradas pelo Prof. Dr. Marcelo Rodrigues Arêas, o backend foi completamente construído sob o estilo arquitetural de Microsserviços e implementado em Python 3.12 com o micro-framework assíncrono FastAPI.

Justificativa Arquitetural da Adoção de Python / FastAPI: A adoção do Python 3.12 com suporte nativo a corrotinas (asyncio), drivers assíncronos de alta performance (asyncpg para PostgreSQL e aio-pika para RabbitMQ) e validação declarativa de contratos via Pydantic v2 possibilitou conciliar código altamente expressivo com velocidade de execução próxima a linguagens compiladas. Essa abordagem mantém 100% dos contratos de eventos, semântica dos padrões de projeto GoF e isolamento de dados sem nenhuma perda de robustez.

2. Padrões de Criação (GoF Creational)

2.1 Factory Method

GoF Criação

Intenção: Definir uma interface para criar um objeto, mas permitir às subclasses ou criadores especializados decidirem qual classe instanciar, eliminando o acoplamento direto entre as camadas consumidoras e as classes concretas.

Aplicação no ArenaHub: No microsserviço de eventos e no microsserviço de pagamento, o padrão Factory Method é utilizado para instanciar dinamicamente as estratégias corretas de cálculo de preço e de processamento bancário:

  • Em services/eventos/src/precos.py: O criador abstrato CriadorPreco expõe o método fábrica criar_estrategia(), implementado por CriadorInteira, CriadorMeia, CriadorPromocional e CriadorCortesia.
  • Em services/pagamento/src/meios.py: O criador abstrato CriadorMeioPagamento declara criar(), implementado por CriadorPix, CriadorCartaoCredito, CriadorBoleto e CriadorCartaoRecusado.
services/eventos/src/precos.py
Python 3.12
from abc import ABC, abstractmethod
from typing import Literal

PoliticaPreco = Literal["INTEIRA", "MEIA", "PROMOCIONAL", "CORTESIA"]

class CriadorPreco(ABC):
    """Criador Abstrato do Factory Method para estrategias de preco."""
    @abstractmethod
    def criar_estrategia(self) -> EstrategiaPreco:
        raise NotImplementedError

class CriadorInteira(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoInteira()

class CriadorMeia(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoMeia()

class CriadorPromocional(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoPromocional()

class CriadorCortesia(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoCortesia()

CRIADORES: dict[PoliticaPreco, CriadorPreco] = {
    "INTEIRA": CriadorInteira(),
    "MEIA": CriadorMeia(),
    "PROMOCIONAL": CriadorPromocional(),
    "CORTESIA": CriadorCortesia(),
}

def criador_para(politica: PoliticaPreco) -> CriadorPreco:
    criador = CRIADORES.get(politica)
    if not criador:
        raise ValueError(f"Politica de preco desconhecida: {politica}")
    return criador

2.2 Singleton

GoF Criação

Intenção: Garantir que uma classe possua apenas uma única instância em todo o ciclo de vida da aplicação e prover um ponto de acesso global e seguro a ela.

Aplicação no ArenaHub: Em serviços assíncronos baseados em event loop, criar conexões dedicadas ao banco de dados para cada requisição HTTP acarreta esgotamento precoce de portas e degradação drástica de performance. Em db.py (presente em cada microsserviço e no API Gateway), o pool de conexões (asyncpg.Pool) é gerenciado como um Singleton de ciclo de vida.

services/ingressos/src/db.py
Python 3.12
import asyncpg
from typing import Optional
from .config import DATABASE_URL

_pool: Optional[asyncpg.Pool] = None

async def obter_pool() -> asyncpg.Pool:
    """Retorna a instancia unica (Singleton) do pool assincrono de conexoes."""
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(
            DATABASE_URL,
            min_size=2,
            max_size=10,
            command_timeout=60
        )
    return _pool

async def fechar_db() -> None:
    """Encerra graciosamente o pool de conexoes durante o shutdown da aplicacao."""
    global _pool
    if _pool is not None:
        await _pool.close()
        _pool = None

3. Padrões Estruturais (GoF Structural)

3.1 Composite

GoF Estrutural

Intenção: Compor objetos em estruturas de árvore para representar hierarquias do tipo "parte-todo". O Composite permite aos clientes tratarem tanto objetos individuais quanto composições de objetos de forma uniforme.

Aplicação no ArenaHub: Localizado em services/eventos/src/estrutura.py. A organização física e comercial de um evento esportivo possui estrutura hierárquica clara:

  • Component (Componente Abstrato): ComponenteEvento declara a interface comum: capacidade(), reservados(), disponiveis(), preco_minimo() e achar_lote().
  • Composite (Composição Raiz): EventoComposto agrega uma coleção de setores esportivos.
  • Composite (Composição Intermediária): Setor (ex.: Pista VIP, Camarote, Arquibancada) agrega lotes de venda.
  • Leaf (Folha Atômica): Lote encapsula a cota física de ingressos, reservas ativas, preço base, política de desconto e janela temporal de vigência.
services/eventos/src/estrutura.py
Python 3.12
from abc import ABC, abstractmethod
from typing import Optional
from datetime import datetime

class ComponenteEvento(ABC):
    def __init__(self, id: str, nome: str):
        self.id = id
        self.nome = nome

    @abstractmethod
    def capacidade(self) -> int: raise NotImplementedError

    @abstractmethod
    def reservados(self) -> int: raise NotImplementedError

    def disponiveis(self) -> int:
        return max(0, self.capacidade() - self.reservados())

    @abstractmethod
    def preco_minimo(self) -> Optional[int]: raise NotImplementedError

class EventoComposto(ComponenteEvento):
    def __init__(self, id: str, nome: str):
        super().__init__(id, nome)
        self.setores: list[Setor] = []

    def adicionar(self, setor: "Setor") -> "EventoComposto":
        self.setores.append(setor)
        return self

    def capacidade(self) -> int:
        return sum(s.capacidade() for s in self.setores)

    def reservados(self) -> int:
        return sum(s.reservados() for s in self.setores)

    def preco_minimo(self) -> Optional[int]:
        precos = [p for s in self.setores if (p := s.preco_minimo()) is not None]
        return min(precos) if precos else None

3.2 Adapter

GoF Estrutural

Intenção: Converter a interface de uma classe na interface que os clientes esperam. O Adapter possibilita que classes com interfaces incompatíveis trabalhem em conjunto.

Aplicação no ArenaHub:

  • Provedor de Pagamento (services/pagamento/src/provedor.py): O núcleo do domínio depende do contrato ProvedorPagamentoTarget. Como a comunicação com instituições financeiras e adquirentes simula APIs proprietárias com formatos heterogêneos de carga útil, o ProvedorSimuladoAdapter traduz a chamada externa para o modelo interno seguro de transação.
  • Canais de Mensageria (services/notificacoes/src/canais.py): O CanalEmailAdapter isola a lógica de entrega de notificações de fornecedores de e-mail transacional (ex.: SES, SendGrid, SMTP).
services/pagamento/src/provedor.py
Python 3.12
class ProvedorPagamentoTarget(ABC):
    """Target: Interface estrita esperada pelas regras de negocio de cobranca."""
    @abstractmethod
    async def processar_cobranca(self, transacao_id: str, valor: int, meio: str, ref: str) -> ResultadoCobranca:
        raise NotImplementedError

class ProvedorSimuladoAdapter(ProvedorPagamentoTarget):
    """Adapter: Converte os formatos da API externa bancaria para o dominio."""
    def __init__(self, api_cliente: ApiExternaSimulada):
        self._cliente = api_cliente

    async def processar_cobranca(self, transacao_id: str, valor: int, meio: str, ref: str) -> ResultadoCobranca:
        raw_resp = await self._cliente.enviar_requisicao_bancaria(transacao_id, valor, meio, ref)
        return ResultadoCobranca(
            aprovado=(raw_resp.codigo_retorno == "00"),
            motivo=raw_resp.mensagem_erro if raw_resp.codigo_retorno != "00" else None,
            tid_operadora=raw_resp.nsu_banco
        )

3.3 Facade e Protection Proxy

GoF Estrutural

Intenção do Facade: Prover uma interface unificada e simplificada para um subsistema complexo.
Intenção do Proxy: Controlar e blindar o acesso a um objeto ou serviço remoto (Protection Proxy).

Aplicação no ArenaHub: Implementados no API Gateway (gateway/src/main.py). O Gateway atua simultaneamente como:

  • Facade: Disponibiliza um único endereço base (http://localhost:8080/api/*) para o frontend React, unificando os 4 microsserviços e abstraindo endereços de rede, portas internas e particionamento de microsserviços.
  • Protection Proxy: Intercepta todas as requisições HTTP, valida a assinatura criptográfica do JSON Web Token (JWT), expurga sumariamente cabeçalhos adulteráveis (x-user-*) e injeta a identidade verificada do usuário (x-user-id, x-user-role) antes de despachar a chamada aos microsserviços.
gateway/src/main.py
Python 3.12
# gateway/src/main.py
@app.api_route("/api/{servico}/{path:path}", methods=["GET", "POST", "PUT", "PATCH", "DELETE"])
async def proxy_catch_all(servico: str, path: str, request: Request):
    """Facade + Protection Proxy: Autentica, higieniza e roteia de forma unificada."""
    headers = dict(request.headers)
    # Expurga headers maliciosos injetados pelo cliente
    headers.pop("x-user-id", None)
    headers.pop("x-user-role", None)

    # Protection Proxy: Valida token JWT
    auth_header = headers.get("authorization", "")
    if auth_header.startswith("Bearer "):
        payload = validar_jwt(auth_header.split(" ")[1])
        if payload:
            headers["x-user-id"] = payload["sub"]
            headers["x-user-role"] = payload["papel"]

    # Facade: Encaminha para a porta interna do microsservico
    return await encaminhar_requisicao(servico, path, request.method, headers)

4. Padrões Comportamentais (GoF Behavioral)

4.1 State

GoF Comportamental

Intenção: Permitir que um objeto altere seu comportamento quando seu estado interno muda. O objeto parecerá ter mudado de classe.

Aplicação no ArenaHub: Três máquinas de estados completas regem a consistência do sistema:

  1. Ciclo de Vida do Evento (services/eventos/src/estados.py): Estados RascunhoState, PublicadoState, VendasAbertasState, VendasEncerradasState, RealizadoState e CanceladoState. Transições proibidas disparam a exceção TransicaoInvalida.

    • Ingresso: EMITIDO → UTILIZADO (ou CANCELADO / INVALIDADO).
  3. Circuit Breaker do Gateway (gateway/src/breaker.py): Estados Fechado, Aberto e MeioAberto.

4.2 Strategy

GoF Comportamental

Intenção: Definir uma família de algoritmos, encapsular cada um deles e torná-los intercambiáveis, permitindo que o algoritmo varie independentemente dos clientes que o utilizam.

Aplicação no ArenaHub:

  • Políticas de Precificação (services/eventos/src/precos.py): Classes PrecoInteira, PrecoMeia, PrecoPromocional e PrecoCortesia. O cálculo de meio-ingresso utiliza divisão inteira com arredondamento comercial superior ((base + 1) // 2), evitando divergência de centavos.
  • Meios de Pagamento (services/pagamento/src/meios.py): MeioPix, MeioCartaoCredito, MeioBoleto e MeioCartaoRecusado (gatilho determinístico para demonstração da compensação da Saga).
services/eventos/src/precos.py
Python 3.12
class EstrategiaPreco(ABC):
    def __init__(self, nome: PoliticaPreco):
        self.nome = nome

    @abstractmethod
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        raise NotImplementedError

class PrecoMeia(EstrategiaPreco):
    def __init__(self): super().__init__("MEIA")
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        return (base_centavos + 1) // 2

class PrecoPromocional(EstrategiaPreco):
    def __init__(self): super().__init__("PROMOCIONAL")
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        pct = max(0, min(100, desconto_percentual))
        return (base_centavos * (100 - pct) + 50) // 100

4.3 Chain of Responsibility

GoF Comportamental

Intenção: Evitar acoplar o remetente de uma solicitação ao seu destinatário, dando a mais de um objeto a oportunidade de processar a requisição através de uma cadeia sequencial de manipuladores.

Aplicação no ArenaHub: Implementado em services/eventos/src/validacoes.py e services/ingressos/src/validacoes.py. Durante o processamento de compra e reserva, o pedido atravessa uma cadeia rigorosa de checagens:

  1. ValidadorEventoExiste: Verifica a existência do evento no banco local.
  2. ValidadorVendasAbertas: Checa se o evento está no estado VENDAS_ABERTAS.
  3. ValidadorLoteAtivoEVigente: Assegura que o lote está ativo e que o timestamp atual encontra-se dentro da janela de vendas.
  4. ValidadorCapacidadeDisponivel: Garante saldo suficiente no lote sem risco de overbooking.
  5. ValidadorLimitePorComprador: Limita o número máximo de ingressos por CPF para prevenir atuação de cambistas.
services/eventos/src/validacoes.py
Python 3.12
class EloValidacao(ABC):
    def __init__(self):
        self.proximo: Optional["EloValidacao"] = None

    def encadear(self, proximo: "EloValidacao") -> "EloValidacao":
        self.proximo = proximo
        return proximo

    @abstractmethod
    def validar(self, ctx: ContextoReserva) -> None:
        if self.proximo:
            self.proximo.validar(ctx)

class ValidadorCapacidadeDisponivel(EloValidacao):
    def validar(self, ctx: ContextoReserva) -> None:
        for item in ctx.itens:
            lote = ctx.evento.achar_lote(item.lote_id)
            if not lote or lote.disponiveis() < item.quantidade:
                raise RegraNegocioViolada(f"Lote {item.lote_id} nao possui lugares suficientes")
        super().validar(ctx)

4.4 Command

GoF Comportamental

Intenção: Encapsular uma solicitação como um objeto, permitindo parametrizar clientes com diferentes ações, enfileirar operações e manter histórico auditável de execuções.

Aplicação no ArenaHub: Em services/ingressos/src/comandos.py, todas as operações de mutação transacional sobre pedidos e ingressos são comandos auditáveis: ComandoReservar, ComandoPagar, ComandoCancelar, ComandoEstornar e ComandoValidarEntrada (check-in no portão da arena com prevenção estrita de leitura duplicada).

Python 3.12
class ComandoValidarEntrada(ComandoPedido):
    """Check-in atômico no portão com prevenção contra uso duplicado de QR Code."""
    def __init__(self, codigo: str, usuario_id: str, papel: str):
        super().__init__(codigo)
        self.codigo = codigo
        self.usuario_id = usuario_id
        self.papel = papel

    async def executar(self, conn: asyncpg.Connection) -> dict:
        ing = await conn.fetchrow("SELECT * FROM ingressos WHERE codigo = $1", self.codigo)
        if not ing:
            return {"aprovado": False, "motivo": "codigo nao encontrado"}
        if ing["status"] == "UTILIZADO":
            return {"aprovado": False, "motivo": "este ingresso ja foi utilizado na entrada"}
        if ing["status"] != "EMITIDO":
            return {"aprovado": False, "motivo": f"ingresso em estado {ing['status']}"}

        res = await conn.execute(
            "UPDATE ingressos SET status = 'UTILIZADO', utilizado_em = NOW() WHERE codigo = $1 AND status = 'EMITIDO'",
            self.codigo
        )
        if res == "UPDATE 1":
            return {"aprovado": True, "motivo": None, "titular": ing["nome_titular"]}
        return {"aprovado": False, "motivo": "concorrencia de leitura: ja utilizado"}

4.5 Observer

GoF Comportamental

Intenção: Definir uma dependência um-para-muitos entre objetos para que, quando um objeto mudar de estado, todos os seus dependentes sejam notificados e atualizados automaticamente.

Aplicação no ArenaHub: No microsserviço de notificacoes (services/notificacoes/src/observer.py), o padrão Observer desacopla a recepção de eventos no RabbitMQ do despacho de avisos aos participantes. A classe DespachanteEventos atua como Subject, gerenciando a lista de observadores especializados (ObservadorCompra, ObservadorEstorno, ObservadorCancelamento).

services/notificacoes/src/observer.py
Python 3.12
class ObservadorEvento(ABC):
    @abstractmethod
    async def notificar(self, topico: str, payload: dict) -> None:
        raise NotImplementedError

class DespachanteEventos:
    def __init__(self):
        self._observadores: dict[str, list[ObservadorEvento]] = {}

    def inscrever(self, topico: str, observador: ObservadorEvento) -> None:
        self._observadores.setdefault(topico, []).append(observador)

    async def despachar(self, topico: str, payload: dict) -> None:
        for obs in self._observadores.get(topico, []):
            await obs.notificar(topico, payload)

5. Padrões Arquiteturais de Sistemas Distribuídos

5.1 Database-per-Service

Padrão Arquitetural

Cada um dos 4 microsserviços de domínio e o API Gateway possuem bancos de dados PostgreSQL completamente isolados: eventos_db, ingressos_db, pagamento_db, notificacoes_db e gateway_db. Não existem comandos JOIN entre bancos nem chaves estrangeiras trans-serviço. O compartilhamento de dados ocorre exclusivamente através de eventos imutáveis com JSON Schemas padronizados.

5.2 Event-Driven Architecture (EDA) & Publish/Subscribe

Padrão Arquitetural

A comunicação assíncrona entre microsserviços é intermediada pelo RabbitMQ 3.13 através de um Topic Exchange unificado denominado arenahub.events. Filas duráveis exclusivas por serviço garantem que eventos de negócio não sejam perdidos caso um serviço esteja temporariamente indisponível.

5.3 Saga Coreografada com Compensações Automáticas

Padrão Arquitetural

Para gerenciar a transação de compra distribuída sem o custo e o bloqueio de transações de duas fases (2PC), o ArenaHub implementa uma Saga Coreografada:

  • Fluxo Normal de Sucesso: Comprador inicia pedido → Ingressos emite compra.solicitada.v1 → Eventos reserva lugares e emite lugares.reservados.v1 → Ingressos solicita cobrança com pagamento.solicitado.v1 → Pagamento aprova cobrança com pagamento.aprovado.v1 → Ingressos gera ingressos digitais com ingresso.emitido.v1 → Notificações avisa o comprador.
  • Fluxo de Compensação (Rollback Distribuído): Se o cartão for recusado ou a compra terminar em 66 centavos, o serviço de Pagamento publica pagamento.recusado.v1. O serviço de Ingressos consome a recusa, cancela o pedido e emite pedido.cancelado.v1. O serviço de Eventos consome o cancelamento e desfaz a reserva, devolvendo os lugares ao estoque de forma idempotente.

5.4 Transactional Outbox Pattern

Padrão Arquitetural

Para eliminar o risco de perda de mensagens entre o commit relacional no PostgreSQL e a publicação no broker, cada serviço implementa a tabela outbox. A mutação de dados e a gravação do evento ocorrem na mesma transação atômica SQL. Um worker assíncrono em segundo plano lê os eventos da outbox com bloqueio de concorrência (SELECT FOR UPDATE SKIP LOCKED), publica no RabbitMQ e apaga o registro após a confirmação de recebimento do broker (*At-Least-Once Delivery*).

5.5 Circuit Breaker (Disjuntor de Falhas)

Padrão Arquitetural

Localizado no API Gateway, monitora a taxa de falhas consecutivas de cada microsserviço. Ao atingir o limiar de 3 falhas consecutivas, o circuito transita para ABERTO e passa a responder imediatamente com HTTP 502 Bad Gateway estruturado, impedindo que requisições presas saturem conexões. Após 8 segundos, o circuito transita para MEIO_ABERTO para enviar uma requisição sonda de teste e avaliar a restauração do serviço.

5.6 Dead Letter Queue (DLQ) & Idempotência

Padrão Arquitetural

Mensagens com falhas de processamento irrecuperáveis são roteadas automaticamente para filas mortas (ex.: notificacoes.events.dlq). O administrador pode inspecionar e disparar o reprocessamento seguro via API (POST /api/<servico>/dlq/reprocessar). Para garantir segurança contra mensagens reentregues, cada serviço mantém uma tabela eventos_processados para filtragem de duplicidades.
