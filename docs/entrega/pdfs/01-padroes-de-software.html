1. Introdução e Contextualização do Sistema

O ArenaHub é uma plataforma moderna e resiliente de gestão de eventos e venda de ingressos voltada para campeonatos de esportes eletrônicos (e-sports), convenções gamer e meetups. O sistema foi concebido para atender picos de tráfego extremos (abertura de lotes concorridos) mantendo estrita consistência financeira, integridade de lotação dos setores e desacoplamento operacional.

Atendendo às diretrizes acadêmicas da disciplina ministrada pelo Prof. Dr. Marcelo Arêas, o backend foi completamente arquitetado com base em Microsserviços e implementado na linguagem Python 3.12 com o framework FastAPI. A escolha do Python assíncrono (I/O não-bloqueante nativo com asyncio, asyncpg e aio-pika) alia expressividade conceitual, segurança de tipos (Type Hints e Pydantic v2) e altíssimo desempenho sob concorrência, dispensando sobrecargas desnecessárias e preservando integralmente os padrões de projeto clássicos do Gang of Four (GoF) e os padrões arquiteturais de sistemas distribuídos recomendados por autores como Martin Fowler, Sam Newman, e Nick Rozanski & Eoin Woods.

Princípio de Conformidade do Grupo 5: Todo padrão de projeto catalogado neste relatório possui correspondência direta, testada e em operação no código-fonte Python dos microsserviços. Os comportamentos foram validados por testes unitários e de integração contínua (end-to-end), comprovando que a mudança para Python mantém 100% dos contratos REST, schemas de eventos JSON e tolerância a falhas.

2. Padrões de Criação (GoF Creational)

2.1 Factory Method

GoF Criação

Intenção: Definir uma interface para criar um objeto, mas deixar as subclasses ou funções especializadas decidirem qual classe instanciar, desacoplando o cliente das classes concretas.

Aplicação no ArenaHub: No microsserviço de eventos (cálculo de preço de ingressos) e no microsserviço de pagamento (processamento por múltiplos meios), o padrão Factory Method é empregado para encapsular a criação das instâncias de estratégias.

  • Em services/eventos/src/precos.py: A classe abstrata CriadorPreco declara o método fábrica criar_estrategia(). Classes concretas (CriadorInteira, CriadorMeia, CriadorPromocional, CriadorCortesia) produzem a respectiva EstrategiaPreco.
  • Em services/pagamento/src/meios.py: A classe abstrata CriadorMeioPagamento declara criar(), implementado por CriadorPix, CriadorCartaoCredito, CriadorBoleto e CriadorCartaoRecusado.
# services/eventos/src/precos.py
from abc import ABC, abstractmethod

class CriadorPreco(ABC):
    @abstractmethod
    def criar_estrategia(self) -> EstrategiaPreco:
        raise NotImplementedError

class CriadorInteira(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoInteira()

class CriadorMeia(CriadorPreco):
    def criar_estrategia(self) -> EstrategiaPreco:
        return PrecoMeia()

CRIADORES: dict[PoliticaPreco, CriadorPreco] = {
    "INTEIRA": CriadorInteira(),
    "MEIA": CriadorMeia(),
    "PROMOCIONAL": CriadorPromocional(),
    "CORTESIA": CriadorCortesia(),
}

def criador_para(politica: PoliticaPreco) -> CriadorPreco:
    criador = CRIADORES.get(politica)
    if not criador:
        raise ValueError(f"Politica de preco desconhecida: {politica}")
    return criador

2.2 Singleton

GoF Criação

Intenção: Garantir que uma classe tenha apenas uma instância e fornecer um ponto global de acesso a ela.

Aplicação no ArenaHub: Em aplicações assíncronas de alta performance (FastAPI + asyncpg), criar uma nova conexão com o PostgreSQL a cada requisição HTTP destrói a escalabilidade do banco de dados. Em db.py presente em cada microsserviço e no API Gateway, o pool de conexões (asyncpg.Pool) é gerenciado como uma instância única compartilhada (Singleton de ciclo de vida da aplicação). As funções obter_pool() e fechar_db() garantem que todas as corrotinas reutilizem o mesmo pool com controle de concorrência atômico. 

# services/ingressos/src/db.py
import asyncpg
from typing import Optional

_pool: Optional[asyncpg.Pool] = None

async def obter_pool() -> asyncpg.Pool:
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(
            DATABASE_URL,
            min_size=2,
            max_size=10,
            command_timeout=60
        )
    return _pool

3. Padrões Estruturais (GoF Structural)

3.1 Composite

GoF Estrutural

Intenção: Compor objetos em estruturas de árvore para representar hierarquias parte-todo. O Composite permite que os clientes tratem objetos individuais e composições de objetos de maneira uniforme.

Aplicação no ArenaHub: Implementado em services/eventos/src/estrutura.py. Um evento de arena esportiva é estruturado hierarquicamente:

  • Componente Raiz (Composite): EventoComposto (agrega um ou mais Setores).
  • Nó Intermediário (Composite): Setor (ex.: Pista VIP, Camarote, Arquibancada; agrega Lotes).
  • Folha (Leaf): Lote (unidade atômica com preço, cota de ingressos, ingressos reservados e janela de vigência).

A classe abstrata ComponenteEvento declara operações como capacidade(), reservados(), disponiveis() e preco_minimo(). O cliente pode consultar a capacidade total ou a disponibilidade restante do evento chamando um único método, e a estrutura de árvore calcula o resultado recursivamente. 

# services/eventos/src/estrutura.py
class ComponenteEvento(ABC):
    def __init__(self, id: str, nome: str):
        self.id = id
        self.nome = nome

    @abstractmethod
    def capacidade(self) -> int: raise NotImplementedError

    @abstractmethod
    def reservados(self) -> int: raise NotImplementedError

    def disponiveis(self) -> int:
        return max(0, self.capacidade() - self.reservados())

class EventoComposto(ComponenteEvento):
    def __init__(self, id: str, nome: str):
        super().__init__(id, nome)
        self.setores: list[Setor] = []

    def adicionar(self, setor: "Setor") -> "EventoComposto":
        self.setores.append(setor)
        return self

    def capacidade(self) -> int:
        return sum(s.capacidade() for s in self.setores)

    def reservados(self) -> int:
        return sum(s.reservados() for s in self.setores)

    def preco_minimo(self) -> Optional[int]:
        precos = [p for s in self.setores if (p := s.preco_minimo()) is not None]
        return min(precos) if precos else None

3.2 Adapter

GoF Estrutural

Intenção: Converter a interface de uma classe em outra interface esperada pelos clientes. O Adapter permite que classes trabalhem juntas quando isso seria impossível por incompatibilidade de interfaces.

Aplicação no ArenaHub:

  • Provedor de Pagamento (services/pagamento/src/provedor.py): O domínio do ArenaHub exige o protocolo ProvedorPagamentoTarget. Como gateway bancário de cartão e PIX é um sistema simulado externo (com formato de resposta proprietário e códigos de status arbitrários), a classe ProvedorSimuladoAdapter adapta a chamada externa ao modelo de dados interno de transação segura.
  • Canais de Notificação (services/notificacoes/src/canais.py): O despachante de notificações interage com a interface CanalNotificacaoTarget. O CanalEmailAdapter encapsula o envio de e-mails, formatando templates HTML e adaptando para o logger sem acoplar o serviço de avisos a um SDK de SMTP proprietário.
# services/pagamento/src/provedor.py
class ProvedorPagamentoTarget(ABC):
    @abstractmethod
    async def processar_cobranca(self, transacao_id: str, valor: int, meio: str, ref: str) -> ResultadoCobranca:
        raise NotImplementedError

class ProvedorSimuladoAdapter(ProvedorPagamentoTarget):
    """Adapta as respostas da API externa simulada para o contrato de domínio."""
    def __init__(self, api_cliente: ApiExternaSimulada):
        self._cliente = api_cliente

    async def processar_cobranca(self, transacao_id: str, valor: int, meio: str, ref: str) -> ResultadoCobranca:
        resposta_externa = await self._cliente.enviar_requisicao_bancaria(transacao_id, valor, meio, ref)
        return ResultadoCobranca(
            aprovado=(resposta_externa.raw_status == 200),
            motivo=resposta_externa.error_description if resposta_externa.raw_status != 200 else None,
            tid_operadora=resposta_externa.nsu_banco
        )

3.3 Facade e Proxy

GoF Estrutural

Intenção do Facade: Fornecer uma interface unificada para um conjunto de interfaces em um subsistema. Define uma interface de nível mais alto que torna o subsistema mais fácil de usar.

Intenção do Proxy: Fornecer um substituto ou marcador de posição para outro objeto para controlar o acesso a ele (Protection Proxy / Smart Proxy).

Aplicação no ArenaHub: Implementados de forma sinérgica no API Gateway (gateway/src/main.py):

  • Como Facade: O cliente web (React) enxerga um único host HTTP (http://localhost:8080/api/*). O Gateway oculta a complexidade interna da malha de 4 microsserviços, roteando chamadas para eventos:3001, ingressos:3002, pagamento:3003 e notificacoes:3004 de forma unificada.
  • Como Protection Proxy: Toda requisição passa por um filtro rígido de segurança. O Proxy descriptografa e valida a assinatura criptográfica do token JWT, descarta qualquer cabeçalho x-user-* enviado maliciosamente pelo cliente externo, e injeta com autoridade os headers internos x-user-id e x-user-role antes de repassar a requisição. Se o token for inválido, o proxy bloqueia a chamada imediatamente com HTTP 401 Unauthorized.

4. Padrões Comportamentais (GoF Behavioral)

4.1 State

GoF Comportamental

Intenção: Permitir que um objeto altere seu comportamento quando seu estado interno muda. O objeto parecerá ter mudado de classe.

Aplicação no ArenaHub: O padrão State é utilizado para modelar os ciclos de vida mais críticos do sistema, evitando estruturas procedurais monolíticas cheias de if/elif/else:

  1. Ciclo do Evento (services/eventos/src/estados.py): Estados RascunhoState, PublicadoState, VendasAbertasState, VendasEncerradasState, RealizadoState e CanceladoState. Cada estado implementa métodos como abrir_vendas(), encerrar_vendas(), publicar() e cancelar(). Transições inválidas disparam a exceção tipada TransicaoInvalida.
  2. Ciclo do Pedido e Ingresso (services/ingressos/src/estados.py): Controla as fases PENDENTE -> RESERVADO -> AGUARDANDO_PAGAMENTO -> PAGO -> CONCLUIDO, bem como o estado final do ingresso (EMITIDO -> UTILIZADO).
  3. Circuit Breaker do Gateway (gateway/src/breaker.py): Disjuntor em três estados clássicos: FECHADO, ABERTO e MEIO_ABERTO.
# services/eventos/src/estados.py
class EstadoEvento(ABC):
    def __init__(self, nome: str):
        self.nome = nome

    def visivel_no_catalogo(self) -> bool: return False
    def aceita_vendas(self) -> bool: return False

    def publicar(self) -> "EstadoEvento": raise TransicaoInvalida(self.nome, "PUBLICADO")
    def abrir_vendas(self) -> "EstadoEvento": raise TransicaoInvalida(self.nome, "VENDAS_ABERTAS")
    def cancelar(self) -> "EstadoEvento": return CanceladoState()

class RascunhoState(EstadoEvento):
    def __init__(self): super().__init__("RASCUNHO")
    def publicar(self) -> EstadoEvento: return PublicadoState()

class PublicadoState(EstadoEvento):
    def __init__(self): super().__init__("PUBLICADO")
    def visivel_no_catalogo(self) -> bool: return True
    def abrir_vendas(self) -> EstadoEvento: return VendasAbertasState()

class VendasAbertasState(EstadoEvento):
    def __init__(self): super().__init__("VENDAS_ABERTAS")
    def visivel_no_catalogo(self) -> bool: return True
    def aceita_vendas(self) -> bool: return True
    def encerrar_vendas(self) -> EstadoEvento: return VendasEncerradasState()

4.2 Strategy

GoF Comportamental

Intenção: Definir uma família de algoritmos, encapsular cada um deles e torná-los intercambiáveis. O Strategy permite que o algoritmo varie independentemente dos clientes que o utilizam.

Aplicação no ArenaHub:

  • Políticas de Preço de Ingressos (services/eventos/src/precos.py): A classe base EstrategiaPreco define preco_unitario(base_centavos, desconto). Estratégias concretas:
    • PrecoInteira: Valor integral (100% da base).
    • PrecoMeia: 50% do valor base com arredondamento seguro.
    • PrecoPromocional: Aplica percentual de desconto configurável no lote.
    • PrecoCortesia: Retorna zero centavos (gratuito para convidados/imprensa).
  • Meios de Pagamento (services/pagamento/src/meios.py): EstrategiaMeioPagamento encapsula o processamento bancário para MeioPix, MeioCartaoCredito, MeioBoleto e MeioCartaoRecusado.
# services/eventos/src/precos.py
class EstrategiaPreco(ABC):
    def __init__(self, nome: PoliticaPreco):
        self.nome = nome

    @abstractmethod
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        raise NotImplementedError

class PrecoMeia(EstrategiaPreco):
    def __init__(self): super().__init__("MEIA")
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        return (base_centavos + 1) // 2

class PrecoPromocional(EstrategiaPreco):
    def __init__(self): super().__init__("PROMOCIONAL")
    def preco_unitario(self, base_centavos: int, desconto_percentual: int = 0) -> int:
        pct = max(0, min(100, desconto_percentual))
        return (base_centavos * (100 - pct) + 50) // 100

4.3 Chain of Responsibility

GoF Comportamental

Intenção: Evitar o acoplamento do remetente de uma solicitação ao seu receptor, dando a mais de um objeto a oportunidade de tratar a solicitação. Encadear os objetos receptores e passar a solicitação ao longo da cadeia até que um objeto a trate.

Aplicação no ArenaHub: Na compra e reserva de ingressos, um pedido deve passar por uma série de verificações obrigatórias de negócio. Em services/eventos/src/validacoes.py e services/ingressos/src/validacoes.py, foi implementado o encadeamento:

  1. ValidadorEventoExiste: Verifica se o evento está cadastrado.
  2. ValidadorVendasAbertas: Confirma se o evento está no estado VENDAS_ABERTAS.
  3. ValidadorLoteAtivoEVigente: Checa se o lote está ativo e se a data atual está dentro do intervalo [inicio_vendas, fim_vendas].
  4. ValidadorCapacidadeDisponivel: Garante que disponiveis >= quantidade.
  5. ValidadorLimitePorComprador: Impede compras abusivas de cambistas (limite de 5 ingressos por CPF).
Cada elo herda de EloValidacao e invoca self.proximo.validar(ctx) somente se sua regra for satisfeita. 

# services/eventos/src/validacoes.py
class EloValidacao(ABC):
    def __init__(self):
        self.proximo: Optional["EloValidacao"] = None

    def encadear(self, proximo: "EloValidacao") -> "EloValidacao":
        self.proximo = proximo
        return proximo

    @abstractmethod
    def validar(self, ctx: ContextoReserva) -> None:
        if self.proximo:
            self.proximo.validar(ctx)

4.4 Command

GoF Comportamental

Intenção: Encapsular uma solicitação como um objeto, permitindo parametrizar clientes com diferentes solicitações, enfileirar solicitações e registrar o histórico das operações para auditoria e reversão.

Aplicação no ArenaHub: No microsserviço de ingressos (services/ingressos/src/comandos.py), todas as transações que alteram pedidos ou ingressos são implementadas como comandos: ComandoReservar, ComandoPagar, ComandoCancelar, ComandoEstornar e ComandoValidarEntrada. Cada comando executa sua lógica de negócio e persiste uma entrada imutável na tabela historico_pedidos, registrando o estado anterior, novo estado, timestamp e justificativa operacional. 

# services/ingressos/src/comandos.py
class ComandoPedido(ABC):
    def __init__(self, pedido_id: str, motivo: Optional[str] = None):
        self.pedido_id = pedido_id
        self.motivo = motivo

    @abstractmethod
    async def executar(self, conn: asyncpg.Connection) -> dict:
        raise NotImplementedError

class ComandoValidarEntrada(ComandoPedido):
    """Executa a validacao do ingresso no portao do evento (Check-in)."""
    def __init__(self, codigo: str, usuario_id: str, papel: str):
        super().__init__(codigo)
        self.codigo = codigo
        self.usuario_id = usuario_id
        self.papel = papel

    async def executar(self, conn: asyncpg.Connection) -> dict:
        ing = await conn.fetchrow("SELECT * FROM ingressos WHERE codigo = $1", self.codigo)
        if not ing:
            return {"aprovado": False, "motivo": "codigo nao encontrado"}
        if ing["status"] == "UTILIZADO":
            return {"aprovado": False, "motivo": "este ingresso ja foi utilizado na entrada"}
        if ing["status"] != "EMITIDO":
            return {"aprovado": False, "motivo": f"ingresso em estado {ing['status']}"}

        res = await conn.execute(
            "UPDATE ingressos SET status = 'UTILIZADO', utilizado_em = NOW() WHERE codigo = $1 AND status = 'EMITIDO'",
            self.codigo
        )
        if res == "UPDATE 1":
            return {"aprovado": True, "motivo": None, "titular": ing["nome_titular"]}
        return {"aprovado": False, "motivo": "concorrencia de leitura: ja utilizado"}

4.5 Observer

GoF Comportamental

Intenção: Definir uma dependência um-para-muitos entre objetos, de modo que quando um objeto muda de estado, todos os seus dependentes são notificados e atualizados automaticamente.

Aplicação no ArenaHub: No microsserviço de notificacoes (services/notificacoes/src/observer.py), o padrão Observer desacopla a recepção de eventos do RabbitMQ da entrega multicanal para os participantes. A classe DespachanteEventos atua como Subject (Sujeito). Observadores especializados (ObservadorCompra, ObservadorEstorno, ObservadorCancelamento) inscrevem-se nos tópicos de interesse e são acionados assincronamente assim que o evento de mensageria é processado. 

# services/notificacoes/src/observer.py
class ObservadorEvento(ABC):
    @abstractmethod
    async def notificar(self, topico: str, payload: dict) -> None:
        raise NotImplementedError

class DespachanteEventos:
    def __init__(self):
        self._observadores: dict[str, list[ObservadorEvento]] = {}

    def inscrever(self, topico: str, observador: ObservadorEvento) -> None:
        self._observadores.setdefault(topico, []).append(observador)

    async def despachar(self, topico: str, payload: dict) -> None:
        for obs in self._observadores.get(topico, []):
            await obs.notificar(topico, payload)

5. Padrões Arquiteturais de Sistemas Distribuídos

5.1 Database-per-Service (Banco de Dados por Microsserviço)

Padrão Arquitetural

Cada um dos quatro microsserviços de domínio e o API Gateway possuem seu próprio banco de dados relacional e usuário restrito no PostgreSQL: eventos_db, ingressos_db, pagamento_db, notificacoes_db e gateway_db. Regra estrita: É proibido qualquer comando JOIN entre tabelas de bancos distintos ou criação de Foreign Keys entre serviços. Toda referência externa é armazenada exclusivamente como UUID opaco, garantindo que o esquema de dados de um serviço evolua sem quebrar os demais.

5.2 Event-Driven Architecture (EDA) e Publish/Subscribe

Padrão Arquitetural

A comunicação inter-serviços baseia-se em eventos assíncronos trafegando via RabbitMQ através de um Topic Exchange unificado (arenahub.events). Filas duráveis com dead-letter configurada garantem que se um consumidor estiver desligado ou sobrecarregado, as mensagens permanecem retidas com segurança no broker.

5.3 Saga Coreografada com Transações Compensatórias

Padrão Arquitetural

Em sistemas distribuídos, manter transações ACID distribuídas (2PC) degrada gravemente a disponibilidade e o particionamento (Teorema CAP). O ArenaHub resolve a consistência eventual através do Padrão Saga Coreografada:

  • Caminho Feliz: compra.solicitada.v1 (Ingressos) -> lugares.reservados.v1 (Eventos) -> pagamento.solicitado.v1 (Ingressos) -> pagamento.aprovado.v1 (Pagamento) -> ingresso.emitido.v1 (Ingressos) -> Notificação ao comprador.
  • Caminho Compensatório (Rollback Distribuído): Se o cartão for recusado ou a compra tiver valor com 66 centavos, o serviço de Pagamento publica pagamento.recusado.v1. O serviço de Ingressos reage emitindo pedido.cancelado.v1. O serviço de Eventos consome o cancelamento e desfaz a reserva, devolvendo os lugares ao estoque de forma idempotente. O participante é devidamente avisado sobre a recusa.

5.4 Transactional Outbox Pattern

Padrão Arquitetural

Garante que uma alteração no banco e a emissão do respectivo evento de negócio ocorram de forma 100% atômica. O evento é gravado na tabela local outbox dentro da mesma transação SQL que altera a entidade de domínio. Um worker em background em cada serviço lê a outbox com SELECT ... FOR UPDATE SKIP LOCKED, publica a mensagem no RabbitMQ e a remove da outbox somente após confirmação do broker.

5.5 Circuit Breaker (Disjuntor de Falhas)

Padrão Arquitetural

Localizado no API Gateway (gateway/src/breaker.py), protege o ecossistema contra falhas em cascata. Ao detectar 3 falhas consecutivas de comunicação (timeout ou connection refused) com qualquer microsserviço, o disjuntor do serviço específico transita de FECHADO para ABERTO. Requisições subsequentes são barradas na borda imediatamente com código HTTP 502 Bad Gateway e payload estruturado, evitando enfileiramento de requisições perdidas. Após 8 segundos, o disjuntor entra em MEIO_ABERTO e envia uma requisição sonda para testar se o serviço se restabeleceu.

5.6 Dead Letter Queue (DLQ) e Consumidores Idempotentes

Padrão Arquitetural

Mensagens com falha permanente não travam a fila principal nem somem em silêncio: são encaminhadas automaticamente para a DLQ do respectivo serviço (ex.: notificacoes.events.dlq). Além disso, cada consumidor mantém uma tabela eventos_processados (armazenando evento_id como Primary Key). Repetições de entrega por oscilação de rede são ignoradas com segurança.
